Common Failure Pattern
The ticket exists. The process behind it does not.
What is happening

A problem ticket is created automatically — but the process that should drive it forward is absent or incomplete.

The specific gaps

· No structured PIR feeds the problem record with verified incident data
· No Problem Manager reviews it with authority or assigns investigation with clear direction
· RCA SLAs exist but breach regularly
· RCA forms are completed — but required fields are answered without sufficient root cause detail
· The output exists on paper; the understanding does not

What ITIL 4 requires

An RCA must produce a documented root cause — not just a completed form. Activity is not the same as value. Until root cause is identified, the problem record cannot legitimately reach Known Error status or closure.

The consequence

The next P1 inherits the same unresolved failure. The cycle repeats.

ITIL 4 · Post-Incident Review
Simple PIR Structure
Section 1
Incident Timeline Review
What happened and when. Walk the full sequence from first alert to service restoration.
Section 2
Detection & Response
Was the incident detected fast enough? Were the right people engaged at the right time? Were escalation paths followed?
Section 3
Resolution Review
What fixed it? Were there faster options? Was the correct workaround or technical action taken?
Section 4
Communication Review
Were stakeholders informed correctly and on cadence? Were parent and child tickets updated?
Section 5
Contributing Factors
What conditions made this failure possible? Process gaps, tooling gaps, knowledge gaps.
Section 6
Action Items
What changes to process, tooling, or training result from this incident? Each item needs a named owner and a deadline.
ITIL 4 · Service Management · Process Reference

Major Incident Management ends at restoration.
Problem Management begins there.

Problem Management vs Major Incident Management Practices

Major Incident Management — Goal
Restore service. Fast.
Speed is the goal. Root cause is explicitly out of scope. Success = service back online.
Problem Management — Goal
Prevent recurrence. Permanently.
Understanding over urgency. This practice cannot begin meaningfully until the incident is closed.

Step 5 · Problem Manager · Facilitates PIR
PIR Facilitated & Outputs Captured
Problem Manager runs the PIR. Outputs feed directly into the problem record: confirmed timeline, contributing factors, open questions about what caused the failure. This is not RCA — it is the structured input that makes RCA possible.
Step 6 · Problem Manager
RCA Assigned to Technical Team
Problem Manager reviews PIR outputs, scopes the investigation, and assigns RCA to the appropriate technical team with a named owner. An SLA is assigned — but meeting it requires active follow-through from the Problem Manager, not just the notification.
Assigned Technical Team · Performs RCA
Root Cause Analysis
Technical team investigates using structured methods — 5 Whys, Fishbone, or timeline analysis. Findings include root cause and contributing process factors. Results returned to Problem Manager for review.

Step 7 · Problem Manager
Known Error & Workaround Assessment
Root cause is documented. If a workaround exists, it is recorded and the problem record is updated to Known Error status. If no workaround exists, the problem remains open pending a permanent fix. Permanent fix options evaluated and decision made.
Step 8 · Problem Manager → Service Desk
Workaround Communicated Back to Service Desk
ITIL 4 requires this step explicitly. Once a workaround is documented, it must be shared with the Service Desk so future incidents of the same type can be resolved faster — without starting from zero. This is the feedback loop that makes the KEDB useful in practice, not just in theory.
Step 9 · Resolution Path
Path 1
Permanent Fix Approved
Change raised, implemented, and verified via change pipeline. Problem record closed with documented resolution.
Path 2
Risk Formally Accepted
Named owner documents rationale. Known Error remains in KEDB with active workaround. Problem record closed.
Path 3
Fix Deferred
Workaround active in KEDB. Problem record stays open. Periodic review scheduled until fix is approved or risk is formally accepted.
// Ideal State vs Reality — For IT Managers & Directors
Ideal State · Problem Management
A named Problem Manager exists and has authority
· Every P1 closure triggers a PIR within 48–72 hours — not optionally
· The Problem Manager facilitates the PIR and owns all outputs
· RCA is assigned with a named technical owner and a hard deadline
· Root cause drives a documented outcome — Known Error, permanent fix, or formal risk acceptance — not just a closed form
· Workarounds are communicated back to the Service Desk
· Problem records close on documented resolution or formal risk acceptance
What Most IT Shops Actually Have
Problem Management as a ticket category, not a practice
· Problem ticket created automatically — no one owns it with authority
· PIR is skipped or treated as optional
· RCA assigned to a team with no facilitation, no deadline enforcement
· Forms are completed but root cause is rarely identified with sufficient detail
· Workarounds are not communicated — Service Desk starts from zero on repeat incidents
· Tickets breach SLA regularly and are closed administratively
The Core Principle — ITIL 4
Activity is not the same as value. Completing a form is not the same as finding a cause.
ITIL 4 defines the purpose of Problem Management as reducing the likelihood and impact of incidents by identifying actual and potential causes — and managing workarounds and known errors. A problem ticket that closes without a documented root cause has produced activity, not value. The measure of a mature Problem Management practice is not ticket volume or closure rate. It is whether the same incident recurs.
// Three Terms — Defined Without Jargon
Temporary Fix
Workaround
An action that reduces or eliminates the impact of an incident without resolving the underlying cause. The system is running again, but the flaw that caused the failure still exists.
"Rolling back the image restored service. We still don't know why the new image broke production."
Documented State
Known Error
A problem where root cause has been identified and a workaround is documented — but no permanent fix has been applied yet. The key word is known: it is logged, owned, and visible. Not the same as resolved.
"We know the deployment fails when a config variable is missing. Rollback is the workaround until we fix the pipeline."
The Library
KEDB
Known Error Database. The searchable repository where all Known Errors are stored. When a new incident occurs, the Service Desk checks the KEDB first — so they are not starting from zero on a problem already analyzed.
"The KEDB had the config variable issue documented. The team applied the workaround in minutes instead of hours."
